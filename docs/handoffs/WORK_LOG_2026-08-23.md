### 1. The QR scanner was never reading a camera (`665d05e`)

New file: `frontend/components/common/qrScanner.jsx` (+219).

The Scan screen had no camera at all. It requested the camera permission in
the permissions gate, discarded the stream immediately, then displayed a
single hardcoded QR labelled "Tap to simulate scanning" whose payload was
already in memory. `jsqr` was listed in `package.json` and imported by
nothing. Scanning appeared to work while no frame was ever read from a lens.

`QrCameraScanner` is a drop-in replacement for that tap: it emits the raw
decoded string to the same `handleQrScanned` callback in `App.jsx`, so the
entire downstream flow (`decodeGloobalQR`, the already-used-code guard, payee
resolution, PIN, biometrics, the payment) is untouched.

Design decisions recorded in the file:

- **Decode every 3rd frame** (`QR_SCAN_FRAME_INTERVAL = 3`) — ~20 checks/sec.
  Decoding all 60 fps burns battery and main-thread time for no gain; a QR
  held to a camera does not appear and vanish inside 100 ms.
- **Downscale frames to ~640 px** (`QR_SCAN_MAX_DIM = 640`). A phone hands
  back 1920x1080+, and jsQR's cost scales with pixel count — a bigger image is
  harder to read, not easier.
- **`lastCodeRef` dedupe.** A steadily-held QR would otherwise fire
  `onDetected` ~20x/sec, re-resolving the same payee repeatedly and racing the
  "code already used" guard against itself.
- **`pausedRef`** rather than reading the prop, so a pause takes effect on the
  next frame instead of requiring the animation loop to be torn down.

State machine: `starting` -> `running` | `denied` | `unavailable` | `error`.

### 2. The QR code itself did not scan (`665d05e`)

`frontend/components/common/gloobalQRCode.jsx`.

Two independent defects:

**Too many branded symbols.** Every dark data module — roughly 400 on a 33x33
code — was being rendered as a dial symbol instead of a filled square. A
decoder samples each module's centre and asks one question: dark or light. A
minus is a thin bar; a plus and a cross are thin strokes; an equals is two
bars and a gap. With several hundred side by side the binariser sees texture
rather than a grid, fails to resolve the module pitch, and gives up before
error correction is even reached. Verified by decoding the rendered image with
real jsQR: `null`, every time.

Fix: `QR_SYMBOL_MODULE_COUNT = 18`. The chosen 18 sit among ~400 solid dark
squares, so the grid resolves normally; even if all 18 misread, that is a
~1.6% error rate against a much larger error-correction budget. Selection is
via `qrPickSymbolModules` — hash every candidate `(row, col)`, sort by hash,
take the first N. The hash ordering scatters them instead of clustering (a run
of adjacent low-ink cells is exactly what confuses binarisation), and being
pure arithmetic it renders pixel-identical for the same payload every time.

**One colour too bright.** Scanners binarise near luminance 128. The orange
`#EA580C` has luminance 123 — five points of margin, which survives a clean
screenshot but not a real camera with glare or an exposure shift. Replaced
with `#C2410C` (luminance ~97), putting all six colours in a 92-102 band, ~30
points clear.

Also removed: the centre logo, which sat over live data modules as pure
decoration at some cost to the error-correction budget.

### 3. Creator Share receipts showed the wrong transaction ID (`665d05e`)

`backend/core/transaction/transactionSnapshot.js`,
`backend/services/api/gloobalApi.js`.

Paying a merchant and receiving that merchant's Creator Share back were both
labelled with the *payment's* ID. They are two different movements between two
different pairs of parties (me -> Jio, then Jio -> me), and a reference that
cannot tell them apart cannot be used to look either up.

The server had been minting a genuine second `Transaction` row for the share
all along (`mintShareLegAndReceipts` in `lib/merchantShareFlow.js`), with its
own `referenceId` and a `metadata.paymentReferenceId` back-pointer, and
returning it as `shareTransaction`. **The client was discarding it.**

- `sendTransaction` now normalises `shareTransaction` through — to `null`
  rather than `{}` when absent, because a 0%-share payee legitimately has no
  share leg and an empty object would read as "there is one, with no id".
- `buildTransactionSnapshot` takes `shareTxnId` / `shareAmount` and stamps
  `shareTxnId`, `shareSourceTxnId` and `shareAmount` onto both the receipt and
  the history entry, empty when there is no share leg.

### 4. My Assets and PayLater reset on every login (`665d05e`)

`backend/services/api/gloobalApi.js`, `backend/domain/FinancialCore.js`,
`backend/domain/essentials/EssentialsService.js`.

`GET /api/assets/:symbolId` and `GET /api/assets/paylater/:symbolId` have
existed on the backend the whole time and **nothing in the client ever called
them.** The screens are projections of the local in-memory ledger, which is
rebuilt from nothing on every page load. Nothing was being lost — it was never
being fetched.

Three new pieces:

- **`GloobalApi.getAssets` / `getPaylater`** — both fail soft, returning
  `null` on a failed read, which callers must distinguish from a genuinely
  empty account. Returning zeroes on a failed read would be the same class of
  invention as the local opening float that once made the dashboard show a
  balance the server had not sent.
- **`reconcilePaylaterDue(serverDues)`** — mirrors the existing
  `reconcileBankBalance`. Deliberately reconciles the **aggregate**
  `pendingDues`, not the row list: the server sends only the 50 most recent
  rows, so replaying them overstates the due the moment a charge is still in
  the window but its repayment has scrolled out. Guards against
  `Number(null) === 0` wiping a real due. `paylaterPayable` is a liability
  account, so entry directions are the mirror of the bank's. This mattered
  beyond display — `RiskEngine` reads `paylaterAvailable` off the same
  balance, so a re-login showing a zero due would have authorised spending
  against already-used credit.
- **`hydrateGrantsFromServer(serverSeeds)`** plus a new
  `EssentialsService.restoreGrant`. Restores **only into an empty grant
  list**, and that restriction is load-bearing: a seed planted this session is
  keyed by its `txnId`, the same seed read back from the server is keyed by
  the server's row id, and `computeSeed` does not return `transactionId`, so
  there is no shared field to match on. Merging would double-count — 20 earned
  showing as 40 — and since the PayLater *limit* is the sum of seed values,
  that is inflated credit `RiskEngine` would authorise real spending against.
  Also converts the server's `yearsAccrued` into the local `monthsAccrued` at
  the boundary, so a year-old seed is not valued as a month-old one.

`restoreGrant` is kept separate from `addGrant` rather than being a flag on
it: `addGrant` mints a grant a payment just earned (always `monthsAccrued: 0`,
today's date, its own key); `restoreGrant` re-creates a past one and must keep
its elapsed growth and original date.

**Also**: `createFinancialCore`'s `openingBankBalance` default changed from
`5e3` to `1e4`, to match the server's own `DEFAULT_ACCOUNT_BALANCE` in
`server.js`.

### 5. The app-map button needed a deliberate hold to open (`665d05e`)

`frontend/components/common/appMap.jsx`.

`MAP_DRAG_THRESHOLD` was 6 px — a mouse number, not a finger one. A thumb
tapping a 52 px target routinely slides 8-15 px between touch and release, so
almost every real tap was classified as a drag and the map never opened. The
only presses that worked were unusually still ones, which is exactly why it
felt like the icon needed a long hold.

Fix: threshold raised to 12 px, **plus** a duration escape hatch —
`MAP_TAP_MAX_MS = 250` with `MAP_TAP_SLOP = 24`. A fast thumb flick can cover
20 px and still be unmistakably a tap. Distance alone cannot separate those;
distance plus duration can. Either test passing counts as a tap.

### 6. Pinch-zoom disabled (`f3bbaa1`)

`gloobal-essentials-preview/index.html`.

This is an app shell, not a document — zooming detaches the fixed-position
overlays (scanner, receipts, app-map button) from the viewport they are pinned
to. Three mechanisms, none redundant:

- `maximum-scale=1.0, user-scalable=no` on the viewport meta — covers Android
  and desktop. **iOS Safari has deliberately ignored `user-scalable=no` since
  iOS 10**, so this alone is not enough.
- A `touch-action` rule that drops the pinch gesture while keeping scrolling.
- A gesture-event handler for iOS.

### 7. History rows had a blank icon (`f3bbaa1`)

`frontend/features/history/TransactionRow.jsx`.

The row icon was a coloured square rendering `t.flag`, the counterparty's
country flag. Most rows have no flag: a Creator Share grant has no
counterparty country, and a row restored from the server carries none either,
so the square rendered empty. A blank tinted box on every line reads as a
broken avatar, not a design.

Replaced with `<FlipSymbolCircle size={36} />` — the same living flip-symbol
mark My Assets and the Referral Network already use, so the three lists look
like one app. The country is still shown on the receipt the row opens.
