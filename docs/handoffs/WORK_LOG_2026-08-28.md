## 2. The live payment failure — investigation

### 2.1 What the message actually came from

`server/server.js:4311` built the string the phone displayed. The `US` was
correct; the `undefined` was the second interpolation.

### 2.2 Currency resolution was never broken

Checked before anything else, because that is what the message appeared to
accuse:

| Check | Result |
|---|---|
| `Country` documents in production | 194 |
| `Currency` documents in production | 142 |
| `US` in the Country collection | `USD` |
| `resolveCountry("US")` | `US/USD` |
| All 194 country rows carry a currency | Yes, none blank |
| All 94 accounts resolve to a real currency | Yes |
| Receiver account | `countryIso: "US"`, no currency field (by design) |

`server/lib/countryCurrency.js:71` `resolveCountry` returns either `null` or a
real uppercase currency code. It is structurally incapable of returning an
object whose `localCurrency` is undefined. Production therefore could not have
resolved a currency to undefined, and did not.

The two country→currency maps were also compared directly:
`server/data/countryCurrencyMap.js` and `backend/data/countries.js` each hold
**194 entries with zero disagreements**. The server is authoritative; the
frontend copy agrees with it.

### 2.3 Defect 1 — why the payment was refused

Six `CountryCurrencyPool` rows in production sat at `totalBalance 0`,
`availableBalance 0`, `reservedBalance 0`:

```
IN local=INR counter=USD    available=0        total=0
US local=USD counter=INR    available=0        total=0
IN local=INR counter=BDT    available=0        total=0
BD local=BDT counter=INR    available=0        total=0
IL local=ILS counter=INR    available=0        total=0
IN local=INR counter=ILS    available=0        total=0
```

Against corridors created later, which all worked:

```
IN local=INR counter=MXN    available=4985166.50
MX local=MXN counter=INR    available=5002633.69
GB local=GBP counter=INR    available=5002155.58
IN local=INR counter=GBP    available=4720129.72
US local=USD counter=GBP    available=4999868.18
GB local=GBP counter=USD    available=5000097.00
```

`CountryCurrencyPool.loadOrCreate` seeds a new pool with
`DEFAULT_POOL_SEED_BALANCE` (5,000,000) through `$setOnInsert`. It has not
always done so. Rows inserted before that change opened at the schema default
of 0, and `$setOnInsert` only applies to documents it actually inserts — so
the day seeding was added, every older row kept its zero permanently.

Those corridors could never recover by being used, because nothing can credit
a pool that no payment is allowed to use. The liquidity gate at
`server/lib/settlementEngine.js:263` refused correctly: `availableBalance 0 <
58.82`. The data was wrong, not the gate.

### 2.4 Defect 2 — why it said "undefined"

`InsufficientPoolLiquidityError` records the released currency as `.currency`.
`server.js` read `.counterCurrency`, a property that class has never had. The
interpolation was therefore always the literal string `undefined`.

The same class was also constructed with four positional arguments against an
object-destructuring signature on the GEU redemption path
(`server.js:5931`), which left **every** field undefined there — including in
the message the error exists to produce.

This is the defect that cost the most time. It made a working currency
resolver look broken and sent the investigation in the wrong direction.

## 3. The code fix

Branch `fix/unseeded-corridor-pools`, commit `44fd010`, merged as `8031a95`.

### `server/lib/settlementEngine.js` (+112)

- **`UnseededCorridorPoolError`** — a corridor that was never opened, distinct
  from one that ran dry. The two need opposite answers: a drained corridor is
  "try again later"; a never-opened one will not return without an operator,
  so telling the payer to wait is telling them to wait for something that
  cannot happen.
- **`UnresolvedCurrencyError`** and **`assertResolvedCurrency`** — refuses
  before a pool key can be built from an undefined currency. The pre-existing
  cross-check compares the caller's currency against the country record and
  passes when they are equal, so it could not catch a side that was undefined
  on both halves.

### `server/models/CountryCurrencyPool.js` (+23/-1)

- **`seededAt`**, stamped by `loadOrCreate` on insert. The three balances
  cannot distinguish a never-opened pool from one drained to exactly zero, and
  those two states need opposite answers. Null on every pre-existing row —
  which is exactly the population needing identification.

The unseeded test is `!seededAt && all three balances 0`. Both halves are
required: `seededAt` alone would flag every healthy legacy row (GB/INR and
friends carry no stamp either), and zero balances alone would flag a genuinely
drained corridor.

### `server/server.js` (+97/-6)

- `.counterCurrency` → `.currency` in both liquidity messages and the audit
  metadata.
- The positional constructor call corrected to object form.
- Both new errors handled with their own precise responses.
- The same never-opened check added to the GEU redemption path.

### `server/scripts/repair-unseeded-pools.mjs` (new, 135 lines)

Dry-run by default. Refuses any pool a `Settlement` references (drained, not
unseeded — that case wants a human) and any pool whose `localCurrency`
disagrees with its `Country` row. Idempotent: a second run finds nothing.

### `server/tests/corridor-currency-integrity.test.mjs` (new, 540 lines)

19 tests. Wired into `npm test` and given its own
`npm run test:corridor-integrity`.

**No country-specific logic was added.** The production-code diff contains no
country or currency literal; this was verified by grep over the diff. The
194-country configuration remains authoritative.

## 10. Auto-deploy — root cause confirmed

The push of `8031a95` produced **no automatic deploy on either target**.
Render went live only because it was deployed manually from the dashboard.

Render's own build log states the cause, on every deploy:

```
==> It looks like we don't have access to your repo, but we'll try to clone it anyway.
==> Cloning from https://github.com/gloobal-pay-gloobal/GloobalV3
==> Checking out commit 8031a95... in branch main
```

**Render's GitHub App has no repository access to `GloobalV3`.** The clone
still succeeds because the repository is public, so builds complete normally
and nothing looks wrong from Render's side — but GitHub delivers push events
only to an App that has been granted the repository. Render is never told that
`main` moved, so no `new_commit` deploy can be created.

This corrects the previous explanation in the docs, which blamed a stale
webhook. That was the symptom; the rename cost the App its grant, and the
missing webhook follows from that. Re-adding a webhook alone does not fix it.

The deploy history matches exactly. Last automatic deploy:
`dep-da23a32d0e5s73eufvf0` at 2026-08-18T10:33:48Z, commit `5ba7464` — days
before the rename. Everything since is `manual`, `api` or `service_updated`.

Netlify is very likely in the same state. It produced no build for `8031a95`;
its recent deploys are recorded `deploy_source: "api"` with
`manual_deploy: false`; and its deploy for `ca13c78` was created 32 minutes
after that commit, where a webhook build starts in seconds. This is strong
evidence but not confirmation — the Netlify App's grant could not be inspected
with the tooling available here.

### The fix (dashboards only — no API exposes App installations)

1. GitHub → org **Settings → Applications → Installed GitHub Apps** →
   **Render** → *Repository access* → add `GloobalV3`.
   <https://github.com/organizations/gloobal-pay-gloobal/settings/installations>
2. Same for the **Netlify** App.
3. Verify by pushing a commit touching `server/` and confirming a deploy
   appears with trigger `new_commit` at the pushed SHA. Nothing less proves
   it — a manual deploy of the right commit is indistinguishable afterwards.
4. The build-log line above should stop appearing.

## 11. Security note

A PDF export of the Render dashboard was placed on the Desktop and offered for
emailing. It was the **Environment** page with values revealed, containing the
full `AUTH_TOKEN_SECRET` and the complete `MONGO_URI` including the database
username and password.

It was not emailed. Sending it would have put the production session-signing
key — which mints tokens for all 94 accounts — and full read/write database
credentials into two mailboxes permanently. The recommendation stands:

- Delete the PDF from the Desktop.
- Rotate `AUTH_TOKEN_SECRET` (this signs everyone out once, by design) and the
  Atlas database password.

One useful thing did come from it: it confirmed the Render environment holds
exactly three variables — `AUTH_TOKEN_SECRET`, `MONGO_URI` and `PORT` — and
that `PROTOTYPE_TRANSACTION_MAX_AMOUNT` is genuinely absent, which is what
makes the live ceiling the code default of 5,000,000.

No secret value is reproduced in this report.
